# 【龙虾时代】harness哲学（一）从 skill 走向orchestrator，基础设施已经变化

这段时间大家聊 harness agent，最热的一个方向大概就是写 skill、做渐进式披露。

这条路当然是对的，而且我一直觉得它很漂亮。上下文是贵的，模型的注意力也是贵的，所以不要把所有规则都提前塞进主 prompt，而是拆成 skill，在需要的时候再给 agent。这样既省 token，又让能力组织得更清楚，不会一上来就把整个系统变成一锅杂糅的说明书。

但我自己在项目里一路做下来，越来越强烈地感觉到：有些需求虽然也能写成 skill，可它们本质上根本不属于“渐进式披露”这套逻辑。

它们不是“等 agent 需要的时候再告诉它”的知识，而是 agent 一进入 session 就应该已经带在身上的东西。它更像启动条件，像地基，像门卡，而不是一本等到出事再去翻的手册。

## 不是所有需求都适合做成 skill

比如一个开发项目真正落到 harness 里，里面有很多事情其实都不是参考信息，而是先验约束。

worktree 该建在哪里，文档该放在哪个目录，文档结构怎么组织，这个项目主要用什么语言，我要求优先使用 `uv`、`python venv` 还是 `conda`，哪些目录 agent 可以动，哪些目录根本不能碰。这些东西如果不是在 session 一开始就被注入，后面很多步骤其实从起跑线就已经歪了。

我后来给这类东西起了个名字，叫“注入性需求”。

这个词听上去有点硬，但意思很简单：它们不是某个任务里临时出现的知识，而是整个项目长期有效、并且应该稳定生效的前提。你不能指望 agent 自己想起来再去看一眼，也不能每开一个 session 都靠人再重复讲一遍。它们最理想的形态，就是项目级自动注入。

现在很多 harness 其实都已经给了这种入口。Claude 有 `CLAUDE.md`，OpenCode 这类工具有 `AGENTS.md`。从设计意图上看，大家做的都是同一件事：给项目准备一个高优先级、长期生效的约束层。

可问题在于，入口有了，不代表事情就真的变简单了。真正难的地方，从来都不是“有没有这个文件”，而是“这个文件到底怎么写，才能写出你自己的工程习惯，而不是别人的模板残影”。

很多人会复制一份现成的 `CLAUDE.md` 或 `AGENTS.md`（比如 Karpathy的），稍微改几个字就开始用。这样当然也能跑起来，但它解决的主要是共性，不是个性。真正进入项目现场后，你很快就会发现，worktree、文档目录、开发语言、环境工具链、主仓库与工作区的隔离方式，这些才是真正决定工程手感的部分，而这些恰恰是模板最难替你写对的东西。

## 我真正想自动化的，其实是 harness 范式本身

拿我自己的习惯来说，我就不喜欢把所有东西都堆在一个仓库、一个工作区、一个默认结构里。我更喜欢把真正的开发工作区做成 `git submodule`，再单独建立 worktree 文件夹。迁出的时候，也只迁出 submodule，而不是把外层工作区一起带走。

这样做的好处很朴素，但非常重要。agent 工作的时候不容易误碰工作区之外的文件；worktree 做隔离开发会自然很多；主开发项目和 harness 工作区也能解耦。我甚至经常希望“纯粹的代码项目”和“保存 harness 资产的项目”是分开的，各自保持纯度。

如果完全手工去做，这些东西当然都能做出来。无非就是每开一个新项目，重复一遍熟悉流程：建 submodule，规划 worktree，复制 `AGENTS.md`，改掉关键字段，再把文档目录、语言规范、工具链偏好一项项补进去。

做完之后，一个项目的 harness 工作区也就算搭好了。

但问题恰恰在这里：agent 时代，agent 本来就是为了自动化而存在的。如果一件事本身高度重复，而且真正需要我拍板的地方就那么几个，那它就不应该继续以手工流程的形式存在。哪怕这个流程已经被你整理得很熟、很模板化，它仍然只是“可复制”，不是“可自动化”。

这也是我做这个项目时最深的一点感受：不要把“可复制”误认为“可自动化”。

## 我先走过一条路：agent 加 skill 组合

我最早其实也走过一条很自然的路：做一套 1 个 agent 加多个 skill 的组合，用固定的几个问题来帮我初始化项目。

你的主目录在哪里，要不要 submodule，文档怎么放，默认语言是什么，工具链偏好是什么，初始化之后要保留哪些约束……这些都可以通过一个 agent 带着几个 skill 来完成。在skill中你可以定义门禁，定义对话链，定义调查事实与临时存储区，单看初始化结果，这套方案其实没什么问题，它确实帮我把重复劳动收敛掉了。

但继续用下去以后，我慢慢发现，问题不在于它能不能初始化成功，而在于**它只在初始化阶段有价值**。

项目一旦初始化完成，这套 agent 加 skill 的组合在绝大多数日常 session 里就不再直接创造价值了。可它还挂在那里，继续消耗 token，继续分散模型注意力，继续占据本来就很紧张的上下文预算。这个开销看上去不一定多夸张，也许只是多出一两百 token，或者几百 token，但当你真的开始追求更干净的 session 和更集中的注意力分配时，这些东西会变得越来越刺眼。

于是就出现了一个有点讽刺的场景：我费了很大劲把初始化能力做成一套 agent 组合，初始化完成之后，我又得想办法把它卸载掉。

说到底，这说明它还是不够自动。

## plugin为什么比skill更像一种组织形式

后来我真正满意的答案，不是“把 skill 写得更聪明”，也不是“把那套 agent 组合再打磨一下”，而是把这件事整体抬升一个抽象层，收敛到 plugin 机制上。

以 OpenCode 为例，我现在更喜欢的做法，是在 agent 启动瞬间直接注入一整套配置。用户层面看到的，不再是我要往项目里搬一个 agent、再搬几个 skill、再改一堆配置，而是只需要挂一行 plugin。就这一行，背后完成的是一整套初始化能力的装载。
```json
{
  "plugin": [
    "file:///ABSOLUTE/PATH/TO/dedge-harness-init-guide/dist/harness_init.js",
    "file:///ABSOLUTE/PATH/TO/dedge-harness-init-guide/dist/harness_shell_env_prepare_plugin.js"
  ]
}
```

初始化完成之后，卸载也同样简单。把那一行注释掉，这组能力就退出了；后面如果需要修复、重建、重新初始化，再把它解除注释就行。对我来说，这件事最重要的意义不是少写几行配置，而是能力管理终于被提升到了编排层。

以前你维护的是一个个 skill。现在你装卸的是一整组能力。看起来只是形式变化，其实抽象层级已经完全不一样了。
```json
{
  "plugin": [
    "file:///ABSOLUTE/PATH/TO/dedge-harness-init-guide/dist/harness_shell_env_prepare_plugin.js"
    // "file:///ABSOLUTE/PATH/TO/dedge-harness-init-guide/dist/harness_init.js"
  ]
}
```
如果要把这个感觉说得更形象一点，我现在越来越相信一件事：**plugin 是 orchestrator 的基础设施。**

skill 更像器官，tool 更像零件，plugin 更像一只手。

手的价值不在于它只是一个部件，而在于它代表的是模块化之后的多功能调度能力。你不会拿一根手指去完成“抓取”这件事，你总是按功能组来调用一整只手。同样的道理，大模型以后如果真的要自己装载和卸载能力，它也一定不是一个个 skill 地去操作，而是按功能组去操作。

这一组东西里可能包含 agent prompt，包含 skill，包含 tool，包含 mcp，包含权限，包含项目级约束，甚至包含装上去和卸下来的时机本身。也就是说，真正有工程意义的从来不是“一个个 skill”，而是“能够完成某类任务的一组能力单元”。

从这个角度看，plugin 就比 skill 更像一种成熟的组织形式。skill 当然重要，但 skill 更像局部知识；plugin 才更像能被 orchestrator 拿来编排、装卸、复用和治理的能力包。

## 为什么我会说，plugin是orchestrator的基础设施

这也是为什么我越来越认同 Anthropic 在那篇文章里提到的 orchestrator 概念。

渐进式披露解决的是“什么时候把某个知识告诉 agent”；而 orchestrator 解决的是“agent 此刻到底应该具备哪一组能力，这组能力由哪些部件组成，它们应该在什么时候被装上，又应该在什么时候被卸下”。

这两者不是替代关系，但在很多 harness 场景里，后者显然更高一层。

因为一个单独的 skill，甚至一个单独的 tool，通常都不能独立构成真正的领域能力。真正的领域能力，几乎总是一个组合：有 prompt 约束，有 skill 指南，有 tool 或 mcp，有项目级配置，还要有生命周期管理。很多时候，连“什么时候装上、什么时候卸下”本身都是能力的一部分。

所以如果今天要让我做一个判断，我会很明确地说：我预言，plugin 会成为 orchestrator 的基础设施。

原因并不复杂。orchestrator 要编排的，从来不是单个知识点，而是一组有边界、有职责、有生命周期的能力模块。而 plugin 恰好天然适合承载这种模块。它既能统一注入，也能统一卸载；既能把多个部件打包在一起，也能保留足够清晰的边界；既适合人手工管理，也很适合以后交给 agent 自己去管理。

你甚至可以说，skill 是语言层的组织，plugin 是工程层的组织。前者让 agent 知道该怎么想，后者让系统知道该给它什么能力。

## 网络上很多项目，其实已经不约而同走向plugin思路了

我觉得一个很有意思的现象是，网上这波 agent 工程项目，虽然名字、包装和目标用户都不一样，但很多最后都不约而同走向了 plugin 思路。

不管是各种 speckit 一类的项目，还是 `superpowers`、`oh-my-openagent`、`get-shit-done` 这些方向，它们表面上看各有各的表达方式，有的强调 workflow，有的强调 prompt 套件，有的强调一键增强，有的强调任务执行力。但如果你往底层看，会发现它们其实都在做同一件事：它们并不满足于只给你一个零散的 skill，而是在试图给你一整组可挂载、可替换、可组合的能力。

换句话说，它们换的已经不只是“某一条提示词”，而是在换一套脑子、一套工作方式、一套能力编排方式。

这一点上，我反而觉得我自己的这个项目挺朴素的。那些项目的 plugin，很多时候换的是脑子；而我的 plugin，至少在当前阶段，更像一个门卡注册程序。它先把项目级的注入性需求稳定挂上去，把入口、结构、权限、工作区拓扑这些前提收拾好，让 agent 一进门就知道自己应该站在哪里、能碰什么、该遵守什么。

但朴素不代表它不重要。恰恰因为它像门卡，所以它更像基础设施。脑子当然重要，可如果连门都进不对、工位都找不准、权限边界都没划好，再聪明的脑子也会在工程现场里四处乱撞。

## 我做这个项目时真正想验证的东西

如果你只是把这个项目看成一个 OpenCode 初始化插件，那你看到的其实只是它的表层用途。

对我来说，它更像一个参考样本，用来验证几个很具体的问题：项目级注入性需求，能不能从手工配置变成自动配置；初始化能力，能不能从常驻 session 变成按需装卸；一组 agent/skill 能力，能不能被 plugin 这种更轻的形式统一托管；harness 的工程约束，能不能被稳定地前置到每一轮 session，而不是依赖模型临场发挥。

从这个角度看，这个仓库讨论的其实不是“怎么多写一个 prompt 文件”，也不是“怎么多做一个 skill”。它真正讨论的是：当 agent 进入工程化阶段后，我们该如何组织甚至卸载能力，而不是如何堆积能力。

如果再往前想一步，plugin 甚至可能都不是终点。未来更自然的方向，很可能是把 plugin 当成一种能力服务、一个程序，甚至一种可被 agent 自己发现、拉取、装配的基础设施。到那个时候，我们讨论的就不再是“这个项目要不要复制一份 `AGENTS.md`”，也不再是“这个 skill 要不要常驻”，而是这个项目当前到底需要什么能力，这些能力该从哪里来，应该保留多久，又该由谁来负责它们的生命周期。

如果真走到那一步，agent 的能力管理就会越来越像软件工程里熟悉的东西：依赖管理、运行时装配、服务编排。那时候我们讨论的，也不再只是 prompt 工程，而是更完整的 agent 工程。

## 最后

在 harness agent 时代，真正值得关注的不只是 skill 本身，我们需要更高一层的组织方式，去管理 agent、skill、tool、mcp 和项目约束之间的关系。

在我看来，plugin 正是这件事通往工程化的入口。它不是 skill 的附件，而更像 orchestrator 可以伸出去抓取、装载、拆卸能力的一只手。

我把这些想法落成了一个具体的参考项目，放在 GitHub：<https://github.com/zztdandan/harness-init-opencode.git>

如果你愿意，也可以把它当成一个很小的样本来看。它当然不是最终答案，但至少能让人从一个相对具体的实现里，看到一点将来 agents 如何被组装、卸载和重新编排的影子。
